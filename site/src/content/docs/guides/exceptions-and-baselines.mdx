This guide tells you how to let code break a rule for now, and keep each case visible. Archangel
has two ways:

- An **exception** is a comment above one import, with the rule and a reason.
- The **baseline** is a file that records each problem that existed when a rule started.

Each check counts both, for each rule, in its summary. So a team can see the numbers go down.
Neither one turns a rule off.

## Write an exception

An exception is a comment directly above the import: above the line of its specifier, or above
the first line of its statement when the statement takes more than one line. It names the rule,
and it gives the reason after a colon:

```ts
// archangel-allow app.feature: checkout shows the cart total until the total moves to shared
import { cartTotal } from '../cart';
```

An exception permits one import to break one rule. Archangel still checks the import against each
other rule. To permit one import for two rules, write two comments on the lines directly above it.
A blank line between a comment and the import breaks the link.

An exception must stay correct as the code changes.

## Use the baseline for old problems

When you start a rule on code that already breaks it, run `archangel baseline add`. It writes each
current problem to `archangel.baseline.json`. A check then fails only for new problems.

- An entry records the rule, the importing file, the import specifier and a count. It does not
  record a line, so an edit above the import does not break the match.
- A check never writes the baseline. When the code fixes a problem, its entry is a
  `baseline-stale` problem. `archangel baseline prune` lowers or removes the entry. It never adds
  one. So the baseline can only get smaller.
- An entry for a rule that the config does not have is also `baseline-stale`. A baseline that is
  not valid JSON stops the check with `baseline-invalid`.

[Add archangel to an existing repository](/archangel/guides/existing-repository/) shows the full
cycle, from `baseline add` to `baseline prune`, with the output of each step.

<Aside type="note" title="A problem without an import">
  An exception is a comment above an import. So it cannot permit a problem that has no import, for
  example a file name or a file with no row in a table. Use the baseline for these problems.
</Aside>

## Which one to use

| You have | Use |
| --- | --- |
| One import that breaks a rule on purpose, with a reason worth reading | An exception |
| Many problems from before the rule existed | The baseline |
| A rule that is wrong for part of the code | Change the rule or the parts, not an exception |
| Files that archangel must not check, such as generated code | The `ignore` key of the config |
| A rule that you do not want, from a preset | The `off` key of the config |

`ignore` takes lines in `.gitignore` syntax. A file that `ignore` removes is not in the check.
