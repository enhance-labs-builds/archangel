This guide checks the architecture of a monorepo with one config at its root. A table says which
apps and packages may use which. A second rule makes each app list the packages that it imports.

## Before you start

- Read [Getting started](/archangel/start/getting-started/).
- Your monorepo uses workspaces of npm, pnpm or Yarn, so that each workspace package is linked in
  `node_modules`.

## How archangel sees a workspace package

An app imports a package of the workspace by its name, for example `@acme/ui`. The package
manager links `node_modules/@acme/ui` to `packages/ui`. Archangel follows the link, as Node and
TypeScript do. So the import goes to a file in `packages/ui`, and a rule about parts judges it as
an import of that file.

<Aside>
  For this reason, an externals set cannot hold the name of a workspace package. Archangel refuses
  the config. Use a part for the folder of the package.
</Aside>

## Make each app list its packages

In a monorepo, a package that one workspace installs is often visible to all of them. An app can
then import a package that its own `package.json` does not list. It works on your laptop and fails
when the app builds alone.

The rule `declared-packages` refuses this. It uses two options:

- `mayNotImport: { packages: ['*'] }` names each outside package.
- `dependency: 'undeclared'` limits the rule to packages that the nearest `package.json` of the
  importing file does not list.

The API imports `zod`. The root `package.json` installs it, but `apps/api/package.json` does not
list it:

<Example fixture="monorepo" file="apps/api/package.json" />

The API also imports `@acme/ui`, which its `package.json` does not list either. The rule does not
refuse it, because the import goes to a file of the repository, not to an outside package. The
table judges it.

To find packages that are only in `devDependencies`, use `dependency: 'dev'`.

## One config or many

Archangel uses the nearest config at or above the folder where it starts. One config at the root
can check all workspaces in one run, and a table can say how they depend on each other. A config
in a workspace sees only that workspace. Use one root config for the rules between workspaces.
