## Your architecture, as a test

A decision such as "features do not import each other" is easy to write in a document. It is
also easy to break with one line in a large change. A reviewer sees the diff, not the graph of
imports.

Archangel makes the decision a test. Give names to the parts of your code. Then write a table:
each row is a part, and the list on the row is what that part may import.

## A rule that cannot fail is a defect

A rule with a wrong path finds no files. It then shows "no problems", the same as a rule that
works. Archangel does not let this occur in silence:

- A part, a group or a table that finds no file is an error.
- Each rule that is not a table row has an example of code that it must reject. `archangel test`
  fails when the rule does not reject it.
- `archangel rules` shows each rule as a sentence, with the files and imports that it judged, and
  the files that no rule judges.
